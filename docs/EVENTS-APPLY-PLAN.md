# /events 活动管理 · 档期应用管线重设计（B+C 融合方案）

> 版本：v1（设计稿）· 2026-11-07
> 范围：改版 bunker / lunar-base 双侧 `/events` 页（event_manager）的「设置面板 + 应用栏」两区
> 选定：**方案 B（指针式激活 + 手术式重建 + 一键应用）** 为骨架，融入 **方案 C** 的区域双页签 / 实时预览 / diff 视图 / 每区一键回滚

---

## 0. 目标与硬约束

**目标**
1. JP 主数据适配（规范名双轨、区域自适应）。
2. 消灭「改名舞」激活与整包重建两大脆弱/慢根源。
3. 路径/备份/激活全部自动化，操作面收敛为「编辑→预览→应用→（必要时）回滚」。
4. 双区（JP/GL）并行管理，互不污染。

**硬约束（不可破）**
| 约束 | 来源 |
|---|---|
| `bin.e` 文件名不变量：JP=`20240405123139.bin.e` / GL=`20240404193219.bin.e` | 服务端 `regionMasterData` 按名取件 |
| 双主数据并存于 `server/assets/release/` | 双区镜像（`db/region_map.json`）|
| 内容式判区（`region.master_edition()`：大小拒读 + AES/msgpack TOC + m_mission 特征）| 文件名无关、防伪装 |
| 四分区写面：`m_event_quest_chapter` / `m_shop` / `m_mom_banner` / `m_mission_term`（含 Start/EndDatetime 控制点）| 现版 rewriter 写面 |
| 月票/竞技场/大狩猎档期**不在本页写面**（各自专表）| 显式范围 |
| 服务端热载：`POST /api/admin/master-data/reload`（Holder.Reload 重建衍生表）| 1.9.0 既定 |
| 无登录单用户设计、改版条带导航样式、零豆腐 | 全局铁律 |

| # | 痛点 | 实况 | 后果 |
|---|---|---|---|
| P1 | 路径门槛 | 必先手选「存放路径」否则应用/保存禁用 | 摩擦大；WSL 盘符映射属非通用文案 |

## 2. 总体架构（B 骨架 + C 元素）

```
┌─ 区域双页签 [JP|GL] ────────────────────────────────┐   ← C
│  [动] [商店] [卡池] [任务]  四档期内联编辑 + 行内校验     │   ← C
│  ┌ 实时预览：本区当前开放（按编辑后状态演算）─────────┐ │   ← C
│  │ 活动 X  12/01–12/31   ▲新  ▼延期                 │ │
│  └──────────────────────────────────────────────┘ │
│  [ 应用到 JP ]   [ 预览 diff ]   [ 回滚点 ▾ ]          │   ← B+C
└──────────────────────────────────────────────────┘

隐形管道（B）：路径默认 → 手术式重建 → 原子替换规范名 →
              自动回滚点（戳+哈希）→ 服务端热载 → 完成
```

**一句话**：用户只面对「哪一区、哪些档期、应用/回滚」；文件路径、激活、备份、部署、热载全部是管道。

## 3. 详细设计

### 3.1 区域双页签（C 元素）
- 顶部 `[ JP ] [ GL ]` 页签；**每区独立状态**（编辑集、待应用集、回滚点列表、活跃哈希）。
- 区域判定：读入该区主数据 → `region.master_edition()` 内容判区 → 校验与页签一致（不一致=红条提示，不写）。
- 规范名按区自动取：JP→`20240405123139.bin.e`、GL→`20240404193219.bin.e`（配置表 `CANONICAL = {"jp": ..., "en": ...}`，取自 `region_map.json` 同源）。
- 两区互斥写锁：同区应用串行；跨区并行允许（不同文件）。

### 3.2 四档期内联编辑 + 实时预览（C 元素）
- 四表行以表格行内编辑（名称/起止时间/启停），行级校验：`Start < End`、与同表冲突检测（同 ID 重叠=红）。
- **实时预览**：编辑态直接演算「当前开放」清单（复用 `/patcher` 的 `summary(items, now)` 同构逻辑），不落盘、不重建。
- 草稿持久化：编辑集存 `drafts/<region>.json`（崩溃可续）；「重置」= 清草稿回到活跃态。

### 3.3 指针式激活（B 核心，替改名舞）
**目录布局**（以桌面为例；机载=app files 内同构）：
```
<release_root>/
  20240405123139.bin.e        ← 规范名（服务端按名取件；保持不变量）
  20240404193219.bin.e        ← 规范名
  .apply/
    active.json               ← 指针清单（原子更新）
    staged/<sha256>.bin.e     ← 重建成品（内容哈希命名）
    history/<utc>-<sha25>.bin.e ← 自动回滚点
    drafts/<region>.json      ← 编辑草稿
```

**`active.json`**（每区一节）：
```json
{
  "schema": "bunker-apply/1",
  "regions": {
    "jp": {
      "canonical": "20240405123139.bin.e",
      "active_sha256": "d2777fec…",
      "activated_at": "2026-11-07T10:30:00Z",
      "history": [
        {"sha256": "…", "file": "history/20261107T103000Z-d277fec….bin.e",
         "label": "apply: 4 表 12 行变更", "created_at": "…"}
      ]
    }
  }
}
```

**激活 = 原子替换**（保文件名不变量）：
1. 重建成品写入 `staged/<sha>.bin.e`（已原子落盘）。
2. **先做校验门**（见 §6）：表数=607、TOC 可解析、四表行数合理、内容判区与页签一致 → 不过=拒绝替换。
3. 自动回滚点：替换前把当前规范名件复制入 `history/`（`os.replace` 之前完成）。
4. `os.replace(staged/<sha>.bin.e, <release_root>/<canonical>)`（同卷原子替换）。
5. `active.json` 原子更新（tmp+replace）：记录新哈希+回滚点入列。
6. 调 `POST /api/admin/master-data/reload` 热载（Holder.Reload 重建衍生表）。

> **为何不改名也不会破坏不变量**：规范名文件始终存在且是「当前生效件」；指针清单只是台账（审计/回滚用），服务端无感知、无需改。

**回滚 = 指针回拨**：
`history/<file>` → `os.replace(…, canonical)` → `active.json` 更新 → 热载。同一条原子链。

### 3.4 手术式重建（B 核心，替整包）
- **只重写变更的四表**：从活跃 bin.e 解析 TOC → 仅对 `m_event_quest_chapter/m_shop/m_mom_banner/m_mission_term` 做**行级 id-anchored 位置编辑**（复用 `build_bin_e.apply_edits` 既定机械：替换三列 = Start/EndDatetime/启停位）→ 其余 603 表**字节原样拷贝** → `packb_lz4`+`attach_exts`+`wrap_toc` 重封装 → `sha256`+`atomic_write`。
- 行数不变（id 锚定，无结构变化）→ TOC 布局可预测、解析风险最小。
- 增/删行（罕见）→ 走整表重写该表（仍不碰其他 603 表）。
- **性能**：四表行级=秒级；字节差≈四表大小（KB 级），非 7.5MB 全量。

### 3.5 一键应用（B 核心）`[ 应用到 JP ]`
单击串成原子链（失败=中途即停并自动回滚到前态）：
```
草稿校验 → 手术重建(staged) → 校验门 → 自动回滚点 → os.replace → active.json → 热载 → 完成
```
- 全程**无需**手动选路径、命名备份、重启服务。
- 进度条按 6 步显示；任一步红=明确报错+已回滚说明。
- 「应用并重建」按钮语义升级为「应用」（重建是管道内部步骤）。

### 3.6 diff 视图 + 每区一键回滚（B+C）
- **预览 diff**（应用前必看/可选自动弹）：
  ```
  [JP] 待应用变更（12 行）
    m_event_quest_chapter  活动「Variation: A. Dynast」  12/01–12/31 → 12/01–01/14  ▲延期
    m_shop                 商店「Shard Exchange」        新增开放 12/05–12/20          ＋新增
    …
  ```
- **回滚点 ▾**：列出本区 `history/`（标签=变更摘要+哈希前 8 位+时间）；选中→「回滚到此」走 §3.3 回滚链。
- 回滚点保留策略：每区最近 50 个（与备份保留同款）；超出自动清最旧。

### 3.7 隐形管道（B）：路径/备份/激活自动化
| 原手操 | 新默认 | 覆写入口 |
|---|---|---|
| 存放路径手选 | 规范落点自动（桌面=`server/assets/release/`，机载=app files） | 「高级」折叠里可改（默认收起）|
| 备份名手填 | 自动=`<UTC戳>-<哈希前8>` | 高级里可加标签 |
| 启用 bin.e 改名舞 | 原子替换+指针台账 | 回滚点 ▾ |
| WSL 盘符映射提示 | **删除**（非通用） | — |

## 4. 数据结构与文件布局

| 件 | 格式 | 原子性 | 说明 |
|---|---|---|---|
| `<canonical>.bin.e` | octo bin.e（AES+msgpack TOC+LZ4 ext）| `os.replace` | 规范名不变量 |
| `.apply/active.json` | JSON | tmp+replace | 指针台账 |
| `.apply/staged/<sha>.bin.e` | bin.e | 写入即完整（atomic_write）| 内容哈希命名 |
| `.apply/history/<utc>-<sha>.bin.e` | bin.e | 复制完成后入列 | 自动回滚点 |
| `.apply/drafts/<region>.json` | JSON | tmp+replace | 编辑草稿 |

**哈希**：SHA-256（`build_bin_e.sha256` 既定）；台账与文件名一致便于审计。

| 方法 | 路径 | 语义 |
|---|---|---|

## 6. 卡载预防（20/40/60%）——B 方案为何不会引入

卡载三断点的经典根因与本方案对策：
| 断点 | 根因 | B 方案对策 |
|---|---|---|
| 20%（主数据）| 规范名缺失/版本串与文件不符/解析失败 | ①规范名**永远存在**（`os.replace` 原子换内容，不是删后建）②校验门（TOC 可解析+607 表+判区一致）**先于**替换 ③版本串=文件 mtime（既定），替换后=新版本→客户端重取且文件在 |
| 40%（资源清单）| catalogs 衍生表陈旧 | 替换后**必调** `POST /api/admin/master-data/reload`（Holder.Reload 重建衍生表=1.9.0 既定），清单与新 bin.e 同步 |
| 60%（资源包）| CDN/octo 死/重启清缓存 | 与本方案无关（部署面）；替换不动 `revisions/0/resources` |

**额外保险**：
- 替换前自动回滚点 → 任何异常一步回拨。
- 校验门含「内容判区与页签一致」→ 防 JP 区误用 GL 件（跨区错配=卡 20% 的另一常见源）。
- 原子替换避免「半写文件」被读到（旧的改名舞崩溃可留半态=卡 20%）。

> 答：**不会**。B 的原子链+校验门+热载三件恰好封住 20/40 两断点的主要根因；60% 属资源部署面不受影响。

## 7. JP/GL 主数据适配（P2 修复的具体落点）

1. **规范名双轨**：`CANONICAL = {"jp": "20240405123139.bin.e", "en": "20240404193219.bin.e"}`（与 `db/region_map.json` 同源）。
2. **判区**：`region.master_edition()` 内容式（大小拒读 64MB + AES+msgpack TOC + m_mission 特征 (10,198,0)/(6,201,0)/(29,7,0)/(1,101030801,0)）→ 页签一致性校验。
3. **四表写面两区同构**（同表名同控制点），仅内容随区（JP=ja 行/GL=fix4 态）。
4. **回滚点/草稿/台账按区隔离**（`.apply/` 内 `regions.jp|en` 分节）。
5. 服务端双区路由（`regionMasterData`）无需改：按名取件不变量已满足。
